iOS feature parity

ios-feature-parity.md · created 2026-09-07 · updated 2026-09-07 · owner umer

The voice overlay's audio half exists on both platforms. Its ongoing-status half is a stub on iOS, where every notification and service function returns a constant. The bridge those functions belong to is already platform-agnostic and already driven by KernelNotifications, so this fills an existing seam rather than designing a new one. This page tracks the whole workstream; only Unit 1 is edited from this branch.

Unit 1 · Settings capability gate IMPLEMENTED, UNTESTED

The Live agent updates row was gated on Platform.OS === 'android', so it could never appear on iOS even once the capability existed. The gate is now the capability itself.

- Platform.OS === 'android' && supportsPromotedNotifications() + supportsPromotedNotifications()

Copy is chosen per platform: iOS names the Lock Screen and Dynamic Island, Android keeps its status-bar island wording verbatim. The existing resume listener already refreshed the enabled flag and now reaches iOS too. The row's action stays openPromotedNotificationSettings, which iOS answers once Mac lands it.

Android is unchanged: the same real capability check that previously sat behind the platform test, and untouched strings. Evidence is a clean typecheck, which is compile-level and says nothing about device behaviour.

Unit 2 · Native Live Activity IN PROGRESS · MAC

Target HerdLiveActivity, bundle com.trymuxr.app.activity, no App Group. Root verified the requirements against official ActivityKit documentation.

It fills the existing bridge rather than adding API. updateNotification starts or updates an activity from the seven scalars the bridge already passes; clearNotification ends it; supportsPromotedNotifications reports real availability, which is what makes the Unit 1 row appear; openPromotedNotificationSettings opens the app's settings page.

No App Group is needed: the activity renders ContentState delivered by ActivityKit and the bridge already carries the complete content model, so nothing requires shared storage. Tap routing uses widgetURL with the existing muxr scheme and the already-entitled applinks:trymuxr.com.

One latent inconsistency to fix along the way: canPostPromotedNotifications returns true on iOS while supportsPromotedNotifications returns false, so the module claims a permission it cannot honour. Nothing user-visible depends on it today because Settings checks both.

Unit 3 · Mute and stop intents STAGED NEXT · MAC

Part of requested parity, not deferred out of it. Android drives mute and stop through notification actions; iOS needs the App Intent equivalent, and iOS already declares onNotificationActionRequested with no sender. Sequenced immediately after the lifecycle path compiles, so the intents are built against a working activity rather than alongside one.

Pending reliable implementation and validation. Compiling is not the bar: the intents must act correctly across the stale, disabled, idle and logged-out states.

Unit 6 · Kitty graphics UNVERIFIED, UNDER DIAGNOSIS

The Kitty renderer is compiled into the existing iOS GhosttyKit. It is not a missing renderer and must not be recorded as one.

The first actual baseline on device produced marker output and no image. Mac is investigating the transport and raw RGB path. Until that diagnosis lands the honest label is unverified and under diagnosis. No config patch is applied on the strength of a guess, and real image, replace, delete, scroll, resize and reconnect behaviour is verified before any config change is considered.

Correction to the original inventory

The first inventory claimed iOS receives no local session notifications. That was wrong. Local lifecycle notifications already exist on iOS. presentPendingLifecycleEvents schedules on every non-web platform including iOS, and Android's scheduleSessionNotification returns early as well. The iOS skip nearby is in applyAttentionCatalog, a fallback used only when the lifecycle catalog is unavailable.

No notification-delivery change should be made on the strength of the withdrawn claim.

Scope limits, unverified or unsupported

None of these may be reported as a runtime pass.

Physical-device voice is unverified. Audio exists in source, but a simulator run aborted in CoreAudio before voice could be exercised and no physical iPhone has been available. Voice must not be reported as passing until it runs on a device.

Remote APNs-driven Live Activity updates are unsupported and out of scope. This workstream updates the activity from the app while it runs. Push-started and push-updated activities are not implemented and are not claimed.

OS background limits apply. Live Activities have system-controlled lifetimes and update budgets, and an app that is not running cannot update one locally. The surface is best-effort and cannot be the only signal that an agent needs attention.

Kitty graphics behaviour is unverified and under diagnosis, not a missing renderer and not a pass.

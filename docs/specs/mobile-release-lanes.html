Proven mobile release lanes

mobile-release-lanes.md · created 2026-08-19 · updated 2026-08-19 · umer

Build once, send every mobile-relevant merge to internal testers, then promote that exact tested binary through a separately protected production lane.

Context

The first store release proved local EAS delivery, but mixed tag creation, native builds, retries and submission. The replacement follows Bluesky's MIT-licensed architecture while keeping Android builds local.

Automatic internal lane

  • Mobile-relevant pushes to main trigger serialized production-signed local builds.
  • EAS remote counters assign unique native build numbers.
  • Artifacts flow to separate submission jobs.
  • Play Internal is polled until the exact version code appears.
  • Fastlane uploads directly to TestFlight; the automatic internal group receives the build after Apple processing.

Protected production lane

  • A manual, protected workflow selects exact tested build identifiers.
  • Android promotes Internal to Production without another build.
  • iOS submits the existing TestFlight build for App Review.
  • A future policy change may automate the same promotion, without changing the build architecture.

Open-source foundation

Expo EAS CLI and Fastlane are MIT licensed. EAS builds both platforms and submits Android; Fastlane uploads iOS directly and handles production promotion. Bluesky's MIT-licensed workflows provide the architecture reference.

Verification

  • □ Workflow YAML and pinned actions validate.
  • □ Fastlane lanes load offline.
  • □ Existing mobile release gate passes.
  • □ Android appears completed in Play Internal.
  • □ iOS finishes processing and appears in the internal TestFlight group.
  • □ Production reuses exact internal build identifiers behind protection.

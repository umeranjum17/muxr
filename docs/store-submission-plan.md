## Form-answer drafts — captain must confirm against binary and policy

**Apple export compliance.** Yes, app uses encryption: standard TLS plus byokit Noise IK/E2EE (`@byokit/seal`/TweetNaCl) for self-hosted pairing and content, not solely OS-provided cryptography. It is not designed to conceal unlawful activity or implement a proprietary algorithm. **Do not answer “no encryption” or assume `ITSAppUsesNonExemptEncryption=false` resolves the form.** Captain/compliance counsel must identify exact algorithms, third-party library distribution, destination territories (including France), whether an exemption from *documentation* applies, whether documentation/CCATS/French filing is required and the final Info.plist flag; attach required documents before review. Prior App Store draft build 40 declared non-exempt encryption false; that is historical state, not a legal conclusion for 0.2.1.

**Apple App Privacy candidate answers.** No operated muxr user account, advertising or tracking/IDFA identified in current source; no developer-operated relay for the self-hosted session. Phone stores revocable pairing credentials; user's own computer receives prompts/files. The relay sees routing/IP metadata but cannot read E2EE content. Local Whisper dictation stays on device. **Open items, not “Data Not Collected”:** iOS Expo push token/notification payload routed through Expo, optional realtime provider may receive microphone audio/transcripts and tool outputs, crash/diagnostic SDKs, site logs and any hosted demo metadata. For each actual recipient mark Apple categories (user content, audio, identifiers, diagnostics, usage) and purposes, linked-to-user, retention and tracking truthfully; distinguish transient data used only to service a request from retained/partner-collected data per Apple's definition. Verify whether notifications expose content to Expo. Confirm user-controlled grant revocation, host data and provider deletion separately. Compare final selections to current console labels, which this API audit could not read.

**Play Data safety candidate answers.** No invented developer collection simply because encrypted user content goes to their own host; E2EE ciphertext not readable by relay may meet Google's exemption. Do not extend that exemption to provider-readable audio/transcripts or Expo push tokens/metadata. Determine collected/shared categories for messages/files/photos, audio, app activity/crash logs, device/push IDs and network/IP data by actual SDK traffic; mark purpose, optional vs required, encryption in transit, retention and deletion mechanism independently. Pairing/revocation is not blanket deletion of third-party/provider data. Self-host LAN may allow cleartext transport at network layer; verify byokit E2EE instead of claiming universal TLS. No precise-location collection merely from mDNS. Inspect current Play answers in Console; the service-account API read-only path cannot report them.

**Play foreground services (declare both).** `microphone`: user starts realtime speech-to-speech in the app; an Android foreground microphone service starts **before** the mic opens, displays a persistent recording notification, runs only during that voice session, and stops on hang-up. It is necessary for audible two-way conversation when the app is backgrounded; no stealth recording, no polling. `dataSync`: when a paired computer has working or attention-needed agents, the foreground-started service keeps its self-hosted relay socket alive so status/attention reaches the phone, with visible herd-status notification. It stops when agents settle or user signs out, yields to microphone during voice, and Android 15's six-hour daily dataSync limit stops it cleanly; reopen refreshes stale status. Attach distinct recorded user journeys, notification and stop evidence for each. Inspect the *merged release AAB* manifest for `FOREGROUND_SERVICE_MICROPHONE`, `FOREGROUND_SERVICE_DATA_SYNC`, service type `microphone|dataSync`, target SDK ≥36 and absence of debug-only overlay/accessibility/storage permissions before answering. Avoid promising unlimited background service.

**Listing drafts (subject to native QA):** App Store subtitle: “Coding agents in your pocket.” Short description: “Control coding agents on your own computer from your phone.” Full description: “muxr pairs with a computer you operate. Watch agent progress, open live terminals, send prompts and browse your project files. Pairing is end-to-end encrypted; the connected computer stays in control. Optional voice requires a provider configured on that computer. Install the open-source host on Mac or Linux to use your own machine, or try the prepared review computer. No muxr account or subscription.” Remove unsupported device/feature claims after candidate QA. No purchase CTA or promise of a muxr-hosted service. Update privacy/support URLs only after checking live deployed pages; iPad screenshots/layout and age rating must match the shipped app.

iOS feature parity

ios-feature-parity.md · created 2026-09-07 · updated 2026-09-07 · owner umer

The voice overlay's audio half exists on both platforms. Its ongoing-status half is a stub on iOS, where every notification and service function returns a constant. The bridge those functions belong to is already platform-agnostic and already driven by KernelNotifications, so this fills an existing seam rather than designing a new one. This page tracks the whole workstream; only Unit 1 is edited from this branch.

Unit 1 · Settings capability gate IMPLEMENTED, UNTESTED

The Live agent updates row was gated on Platform.OS === 'android', so it could never appear on iOS even once the capability existed. The gate is now the capability itself.

- Platform.OS === 'android' && supportsPromotedNotifications() + supportsPromotedNotifications()

Copy is chosen per platform: iOS names the Lock Screen and Dynamic Island, Android keeps its status-bar island wording verbatim. The existing resume listener already refreshed the enabled flag and now reaches iOS too. The row's action stays openPromotedNotificationSettings, which iOS answers once Mac lands it.

Android is unchanged: the same real capability check that previously sat behind the platform test, and untouched strings. Evidence is a clean typecheck, which is compile-level and says nothing about device behaviour.

Unit 2 · Native Live Activity IN PROGRESS · MAC

Target HerdLiveActivity, bundle com.trymuxr.app.activity, no App Group. Root verified the requirements against official ActivityKit documentation.

It fills the existing bridge rather than adding API. updateNotification starts or updates an activity from the seven scalars the bridge already passes; clearNotification ends it; supportsPromotedNotifications reports real availability, which is what makes the Unit 1 row appear; openPromotedNotificationSettings opens the app's settings page.

No App Group is needed: the activity renders ContentState delivered by ActivityKit and the bridge already carries the complete content model, so nothing requires shared storage.

Tap routing uses widgetURL with the existing muxr scheme and the already-entitled applinks:trymuxr.com, and opens the app overview, not a specific session. The payload carries no session route: eventKey is a dedupe key of the form mode:ids that can cover several agents at once, and it is an internal id the product never surfaces. Per-session routing would need a route added to the payload first, so it is neither implemented nor claimed.

One latent inconsistency to fix along the way: canPostPromotedNotifications returns true on iOS while supportsPromotedNotifications returns false, so the module claims a permission it cannot honour. Nothing user-visible depends on it today because Settings checks both.

Unit 3 · Mute and stop intents SHARED PATH IMPLEMENTED · NATIVE PENDING

Part of requested parity, not deferred out of it. Android drives mute and stop through notification actions; iOS needs the App Intent equivalent, and iOS already declares onNotificationActionRequested with no sender.

Shared TypeScript, on this branch. Mac's approved router emits the existing mute action with an optional desiredMuted boolean.

  • The listener passes desiredMuted through and normalises anything that is not a boolean to absent, so a malformed native payload cannot mute a call silently.
  • applyRealtimeMuted(desired?) applies an explicit state as requested instead of toggling, so a repeated mute request leaves the session muted. Omitting it keeps the legacy toggle the Android action and the in-app button still send.
  • With no live session the mute action is a no-op: a stale control never opens the microphone and never leaves a mute flag armed for the next call.
  • A start deferred behind VAD arming has no transport yet. The handle receives the recorded state before it goes live, so a mute requested in that window cannot leave the flag and the Live Activity claiming muted while the microphone opens unmuted.
  • Every call carries a generation token. setVoiceGeneration is an optional native method taking a string and returning nothing: a fresh randomUUID() at the start of a call, and an empty string at teardown so native can tell a real teardown from a replacement and settle a pending stop before cancelling anything else. A module without the method is a silent no-op, so Android is untouched.
  • The action event carries an optional generation, and the handler rejects any supplied generation that is empty or does not match the running call before acting. A queued event from an ended call can never reach the next one. Legacy Android events omit the field and keep their behaviour; a field present but not a string is coerced to empty and rejected rather than read as legacy.
  • The token rotates synchronously at start and teardown, so a stop and start that React coalesces into one render still rotate it. Rotation therefore does not depend on a disconnected snapshot reaching updateNotification, which the effect's own cancellation can drop.
  • stop keeps its existing idempotent teardown path.
  • The start branch is now an explicit action === 'start' test rather than a default else, so an unrecognised action cannot fall through and open a session.

Native side pending, Mac. actionsAvailable gates the controls on a JS listener having been observed and voice being active, hiding stale or unavailable controls rather than showing them dead. Per the Mac and root agreed contract it excludes connecting; the shared deferred-start mute fix does not broaden that gate and no broadening is requested. The intent awaits the reflected updateNotification state under a bounded timeout and reports no local success it has not seen confirmed.

Still pending reliable implementation and validation as a whole. Compiling is not the bar: the intents must act correctly across the stale, disabled, idle and logged-out states.

Unit 6 · Kitty graphics UNVERIFIED, UNDER DIAGNOSIS

The Kitty renderer is compiled into the existing iOS GhosttyKit. It is not a missing renderer and must not be recorded as one.

Until that diagnosis lands the honest label is unverified and under diagnosis. No config patch is applied on the strength of a guess, and real image, replace, delete, scroll, resize and reconnect behaviour is verified before any config change is considered.

Correction to the original inventory

The first inventory claimed iOS receives no local session notifications. That was wrong. Local lifecycle notifications already exist on iOS. presentPendingLifecycleEvents schedules on every non-web platform including iOS, and Android's scheduleSessionNotification returns early as well. The iOS skip nearby is in applyAttentionCatalog, a fallback used only when the lifecycle catalog is unavailable.

No notification-delivery change should be made on the strength of the withdrawn claim.

Scope limits, unverified or unsupported

None of these may be reported as a runtime pass.

Physical-device voice is unverified. Audio exists in source, but a simulator run aborted in CoreAudio before voice could be exercised and no physical iPhone has been available. Voice must not be reported as passing until it runs on a device.

Remote APNs-driven Live Activity updates are unsupported and out of scope. This workstream updates the activity from the app while it runs. Push-started and push-updated activities are not implemented and are not claimed.

OS background limits apply. Live Activities have system-controlled lifetimes and update budgets, and an app that is not running cannot update one locally. The surface is best-effort and cannot be the only signal that an agent needs attention.

Terminal parity and signing carry source-level evidence only. Typecheck, flow tests and syntax checks pass on Linux; no Swift build, archive or export has been run, so native acceptance is not claimed.

Kitty graphics behaviour is unverified and under diagnosis, not a missing renderer and not a pass. The only baseline so far is a simulator run; no physical phone has been tested.

Tap-to-open reaches the app overview, not a chosen session. No session route exists in the notification payload, so per-session routing is neither implemented nor claimed.

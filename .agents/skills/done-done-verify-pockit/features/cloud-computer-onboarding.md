# Start a cloud computer

The native first-run screen opens the cloud checklist. With a linked Boat account the phone creates the machine, installs and starts the muxr host on it, reaches it over SSH with a login key the phone makes and pairs itself through that tunnel with no QR, then lands on Home. The cloud computer never joins a tailnet: Tailscale is only for the person's own devices. Everything runs through `@byokit/cloud@0.3.0` (`apps/mobile/sources/cloud/deployBoatComputer.ts`); the installed PWA says setup must start in the muxr phone app.

## Sub-features

- `first-run-entry`: native cloud entry opens the checklist without changing link pairing or SSH routes.
- `account-link`: email starts the kit claim stream, the sign-in page and short code are shown, **Sign in to Boat** stays tappable while the screen waits, and a completed key is stored only in native secure storage. A stored key skips straight to size and price on the next visit. A sign-in Boat has not finished after 10 minutes stops with "Boat did not finish signing in within 10 minutes. Try again." and a **Try again** button.
- `size-and-price`: Small or Standard with Boat's dated per-hour price and plan floor; nothing is created before **Create cloud computer**.
- `deploy`: `machine().create` once with an idempotency key the kit saves before the create, so a retry after a lost answer gets the same computer back (a retry reuses the stored machine; a failed or gone computer is cleared, the failed one removed; leaving the screen keeps the deploy running and returning never starts a second), then `setup()` (with no `address`, so no tailnet join) installs the published `@trymuxr/cli` as a systemd unit running `MUXR_MODE=selfhost muxr up`.
- `ssh-route`: the checklist's **Private connection** step. The phone makes an Ed25519 login key (`generateSshLoginKey()` in `connection/sshPublicKey.ts`), sends its public half to Boat's `POST /sandboxes/{id}/sshkey` with the person's Boat key, and Boat answers the machine's SSH address, user and host key. The phone opens the Direct SSH tunnel (`establishSshTunnel`) only to the host key Boat gave, with no fingerprint prompt, and stops before signing in if the server shows another key. No browser opens after **Create cloud computer**.
- `pair`: the setup pair gate runs `muxr self-host --configure-only --loopback --install-herdr` (with a fixed `*.ts.net` advertise name nothing dials) then `muxr pair --handoff` on the machine, reads the offer from the kit outbox, pairs through the SSH tunnel and delivers the two words with kit `deliver`. The phone then keeps the SSH route (key in the secure store, pinned target, relay `ws://127.0.0.1:8792`); success lands on Home.
- `web-boundary`: PWA shows the phone-app instruction and never runs provider calls.

## How to get to it (user POV)

Open the unpaired phone app, tap **Cloud computer**, and enter the Boat account email. The sign-in action opens Boat's page; the person approves there and returns to the checklist, picks a size and taps **Create cloud computer**. Nothing else needs a tap: the checklist moves through Create, Put muxr on it, Private connection and Pair with this phone, then Home. The PWA entry opens the phone-app instruction.

Preconditions: use `../SKILL.md` isolation and its native Android + installed-PWA Visual check. Do not run `claim()` against Boat for verification; reuse the fleet's existing key and never capture the short code or a key. **Creating a machine costs money: only after the captain (through firstmate) approves the cost.**

2. Account link without Boat: start `node .agents/skills/done-done-verify-pockit/features/boatSignInLab.mjs <port>` from the repo root, build the release APK with `EXPO_PUBLIC_MUXR_BOAT_API=http://127.0.0.1:<port>/api/v1` and `adb -s $SERIAL reverse tcp:<port> tcp:<port>`. Enter `umer@example.com`, tap **Connect Boat account**, then **Sign in to Boat** while it waits: the browser shows the lab page, and back in the app step 1 reads **Connected** and size and price is next. Record it (`screenrecord`). `BOAT_LAB_APPROVE=never` keeps Boat pending for the 10-minute timeout message. The flow test `apps/mobile/sources/cloud/boatSignIn.integration.spec.ts` drives the same screen on the host.
3. With a stored key, capture the size-and-price step the same way. Stop there unless the cost is approved.
4. Machine side without Boat: `node scripts/diagnostics/application/checkSelfhostState.mjs` proves `--configure-only --loopback` binds 127.0.0.1, serves relay health under `muxr up` and is refused by every reconfigure path; `tests/cross-side/linkPairing.integration.test.ts` covers `pair --handoff`.
5. SSH route without Boat: the second flow in `boatSignIn.integration.spec.ts` drives the real `setup()` and `deployBoatComputer()` against the fake Boat server with a stand-in for Boat's SSH key route and the phone's SSH module, and proves the phone signs in only with the key Boat authorized, to the host key Boat gave, pairs through the tunnel, keeps the SSH route, and never opens a page or runs a Tailscale command.
6. On the emulator, end to end, no Boat and no spend: the `cloud-setup` journey (`features/cloudSetupLab.mjs`, under the emulator lock and a provisioned Herdr lab, with a release APK built with `EXPO_PUBLIC_MUXR_BOAT_API=http://127.0.0.1:<port>/api/v1`) runs `boatSignInLab.mjs` with `BOAT_LAB_SSH=<short dir>`: a stand-in computer (`features/cloudMachineLab.mjs`) in a user and network namespace of its own, named `muxr-cloud`, with a real sshd and this checkout's muxr CLI, its relay on its own loopback 8792. The lab answers Boat's SSH key route with that sshd and runs the app's `self-host` and `pair --handoff` there. At 390 dp (or `CLOUD_LAB_DP=270 CLOUD_LAB_FONT=2.0 CLOUD_LAB_THEME=dark`, applied once the account is linked, scrolling to follow the active step) the journey links the lab account, taps **Create cloud computer** and nothing else, fails if anything opens over muxr, shoots each step (`01-size-and-price` … `06-pairing`) and needs `07-home-connected`; `recording-*.mp4` and `journey.log` land in the evidence folder. The real Boat machine run belongs to its own approved lane; this journey proves the phone path, not Boat's own endpoint.
7. Open the same first-run route in the installed PWA; verify the cloud entry opens the phone-app instruction and no Boat request is made.
8. Real run (approved cost only): Create and expect Home with the cloud computer paired over SSH, no browser and no tailnet. Then remove the machine from the Boat account unless told to keep it.

## Gotchas

- The machine installs the `CLI_TARBALL_URL` and `CLI_TARBALL_SHA256` pins in `deployBoatComputer.ts` (the npm registry tarball, sha256-checked before install); a follow-up after each release moves it (see `docs/RELEASING.md`), nothing checks it automatically. A real run needs a published CLI that has `--loopback`, `--install-herdr` and `pair --handoff`; older releases (0.2.0) fail at "Setting up muxr".
- A claimed key's create scope and Boat's own `POST /sandboxes/{id}/sshkey` answer from the phone are unproven until a real run (BYOKit M6); the lab stands in for both. Boat answers either `sshEndpoint` (`host:port`) or `machineIp` (port 22), plus `hostKey` and `sshUser`.
- `--configure-only --loopback` in the published CLI takes only a `*.ts.net` advertise name, so the app passes a fixed one that nothing dials; the host's own state still names it.
- Boat bills per second while on; the price rows are dated in `deployBoatComputer.ts` and must be rechecked against https://docs.boat.dev/pricing when they age.
- On a fresh AVD the first **Sign in to Boat** tap can leave the app showing for over 30 s while Chrome starts for the first time; tap again before calling it a failure.
